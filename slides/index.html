Part 1 · 核心動機

為什麼不能直接問純 LLM 就好？

大型語言模型（LLM）雖然很會聊天，但如果只靠模型自己回答專業知識，會遇到三個常見煩惱：

1. 知識過期（Static）

模型的知識停在訓練結束那一刻。想讓它學會昨天的新規定，重新訓練一次的費用與時間都非常高。

2. 幻覺問題（Hallucination）

遇到忘記或沒學過的題目時，模型不會停下來查證，反而容易憑機率「一本正經地胡說八道」。

3. 沒看過私有資料

通用模型不知道公司內部手冊或個人筆記，也沒辦法明確指出回答是參考哪份文件的哪一段。

Part 1 · 核心概念

什麼是 RAG？一句話：讓 AI「開書考試」

RAG（Retrieval-Augmented Generation，檢索增強生成）由 Meta AI（Lewis et al., 2020）提出：在回答前，先去外部書架「找資料」，再把查到的段落交給 LLM 整理作答。

純 LLM ＝ 閉書考試

  • 只靠參數記憶（Parametric Memory），也就是背在模型權重裡的舊記憶。
  • 忘記細節時容易用猜的，產生幻覺。
  • 沒辦法隨時替換最新資料。

RAG ＝ 開書考試

  • 結合 LLM 的參數記憶（理解與表達）＋ 外部非參數記憶（可隨時更新的文件庫）。
  • 先翻書找證據，再整理出有憑有據的答案。
  • 更新知識只需換資料庫，不需重訓模型（Hot-swappable）。

Part 2 · 底層原理 I

第一步：把厚文件切成「小吐司塊（Chunking）」

直接把整本 100 頁 PDF 塞進模型既太長又找不到重點，所以我們要先把文件切成好消化的小段落（Chunks）。

切塊（Text Chunking）的用意

  • 不撐爆視窗：避免超出 LLM Context Window，也能省下大量 Token。
  • 檢索更精準：每塊約 300～800 tokens，聚焦單一小主題。
  • 保留 Metadata：同步記錄檔名、頁碼、章節，方便最後標註來源。

貼心設計：Chunk Overlap（重疊）

相鄰兩塊保留 10%～20% 重疊文字（約 50～100 tokens），避免重要句子剛好被切在邊界而斷章取義。

Chunk 1 前半段 10~20% 重疊區 Chunk 2 後半段

Part 2 · 底層原理 II

電腦怎麼懂語意？Embedding 與向量資料庫

傳統搜尋只看「字一不一樣」，RAG 透過 Embedding 把文字的「意思」變成座標，讓意思相近的句子住在一起！

1. Embedding 向量

將文字轉成高維數字座標（如 768 或 1536 維）。語意相近的句子距離非常近。

2. 餘弦相似度

計算問題向量與文件向量的夾角餘弦值（範圍 -1 到 1）。數值越接近 1，代表意思越契合！

3. 向量資料庫

如 Chroma、FAISS、Pinecone、Milvus。運用 ANN（如 HNSW） 演算法，在毫秒內從百萬片段撈出 Top-K。

小柴犬提醒：離線建索引與線上提問，一定要用同一個 Embedding 模型，否則座標系對不起來喔！

Part 3 · 系統架構 I

RAG 階段一：離線索引（先把書架整理好）

在系統上線前或新增檔案時執行，把雜亂的文件變成整齊可搜的向量圖書館：

1. Load 載入

讀取 PDF、Markdown、網頁或資料庫原文。

➜

2. Split 切分

切成 Chunks，保留 Overlap 與 Metadata。

➜

3. Embed 嵌入

用 Embedding 模型將每段文字轉為語意向量。

➜

4. Store 儲存

把「向量＋原文＋Metadata」存進向量資料庫。

新手小筆記

離線索引只需在資料新增或修改時執行，平常使用者問問題時不會重跑，因此回覆速度很快！

Part 3 · 系統架構 II

RAG 階段二：線上查詢與生成（即時開書作答）

當使用者按下送出問題的那一刻，系統會在幾秒內依序完成以下 4 步：

1. Query Embed

用同一套 Embedding 模型把問題轉成查詢向量。

➜

2. Retrieve Top-K

撈出相似度最高的前 K 個段落（常見 K=3~5）。

➜

3. Prompt 增強

組合「系統規範＋Top-K 參考段落＋問題」。

➜

4. LLM 生成

要求 LLM 僅依參考資料作答，並附上出處。

調校小陷阱：Top-K 不是越大越好喔！

Top-K 太小會漏掉答案；設太大除了浪費 Token，還會塞入雜訊並觸發 Lost in the Middle（LLM 容易忽略長文章中間段的重點）。

Part 4 · 實務升級

為什麼基礎 RAG 還是會答錯？三大進階法寶

基礎版（Naive RAG）常因為「問得太口語」、「專有名詞／代碼漏抓」、「排序雜訊」而出錯，實務上會加上三層升級：

檢索前 · Query Rewriting

先請 LLM 把含糊口語改寫成精確查詢句，或拆成多個子問題（Multi-Query），讓檢索更容易命中。

檢索中 · Hybrid Search

同時結合 BM25（關鍵字精確比對）＋向量語意搜尋，再用 RRF 融合排序，專治代碼與專有名詞（如 ERR_4042）漏抓。

檢索後 · Reranking

先快速粗篩 Top-20，再由更細緻的 Cross-encoder Reranker 重新打分，只把最精華的 Top-3～5 交給 LLM。

Part 4 · 品質量化體檢

怎麼幫 RAG 打分數？RAGAS 三角評估法

判斷 RAG 好不好不能只靠體感！業界常用 RAGAS（RAG Triad） 三大指標，快速定位是檢索壞了還是生成壞了：

1. Context Precision
檢索精準度

檢查：問題 ↔ 撈出的段落

撈回來的段落真的跟問題有關嗎？分數低代表切塊或檢索要調整。

2. Faithfulness
忠實度

檢查：撈出的段落 ↔ 生成答案

LLM 有沒有 100% 忠於參考段落，沒有自己憑空腦補或幻覺？

3. Answer Relevance
答案相關性

檢查：問題 ↔ 生成答案

最終答案是否直接、完整回答了使用者的原始問題？

Part 5 · 本週課程亮點

傳統 RAG vs. LLM Wiki：兩種知識哲學大對決

這份可愛簡報本身就是從 LLM Wiki 編譯出來的！看看它和傳統 RAG 差在哪裡：

傳統 RAG：查詢時才臨時拼湊

  • 屬於無狀態（Stateless）檢索。
  • 每次提問才臨時把零碎段落抓出來拼出答案。
  • 問完就忘，知識庫本身不會變更有結構，也不容易發現跨文件矛盾。
  • 超強優勢：處理數十萬～百萬份海量動態文件時無可取代。

LLM Wiki：寫入時就預先編譯

  • 由 Andrej Karpathy 提倡，把 LLM 當成「知識編譯器」。
  • 每次 Ingest 新文章，就主動整理進 wiki/、連上 [[wikilink]] 與記錄 log.md。
  • 知識會產生複利，人類與 AI 都能直接閱讀、審查與版控（Git）。
  • 超強優勢：深度研究、課程學習、個人／團隊活知識庫。
