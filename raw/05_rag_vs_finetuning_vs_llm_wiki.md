# Raw Source 05: RAG 技術選型與 LLM Wiki 對比

- **主題**：RAG vs. Fine-Tuning vs. Long Context vs. LLM Wiki
- **參考來源**：Anthropic Contextual Retrieval、OpenAI RAG vs Fine-Tuning Guide、Andrej Karpathy (2026) LLM Wiki Concept
- **定位**：協助學習者理解不同知識增強方案的適用場景，並連結本課程核心——LLM Wiki。

## 四種常見方案的核心差異

### 1. RAG（檢索增強生成）
- **運作方式**：查詢當下才從外部切塊向量庫中動態撈出片段。
- **優點**：資料可即時更新、成本低、有明確來源引用、適合大量變動資料（如客服知識庫、企業文件）。
- **限制**：屬於**無狀態（Stateless）檢索**——每次提問都重新把零碎的 Chunk 拼在一起，知識不會隨時間「累積、整理或消除矛盾」。

### 2. Fine-Tuning（模型微調）
- **運作方式**：用特定領域資料直接調整模型內部權重。
- **優點**：適合調整語氣、輸出格式、特定領域風格或推理行為。
- **限制**：訓練成本高、資料更新慢、**不適合拿來「背誦頻繁變動的事實」**，仍可能產生幻覺且無法直接附帶來源出處。

### 3. Long Context（超長上下文）
- **運作方式**：直接把整份文件（數十萬 Tokens）全部塞進 Prompt。
- **優點**：架構最簡單、保留完整跨段落上下文、不需切塊與維護向量庫。
- **限制**：每次呼叫的 Token 費用與延遲高，當文件庫達數千份時仍無法全部塞入。

### 4. LLM Wiki（編譯式知識庫）
- **運作方式**：在**匯入資料時（Ingest Time）**就由 LLM 主動閱讀原始資料、整合進結構化 Markdown 頁面、建立 `[[wikilink]]` 雙向連結、標註矛盾並維護索引（`index.md`）與日誌（`log.md`）。
- **與傳統 RAG 的關鍵對比**：
  - 傳統 RAG 是「**查詢時才臨時拼湊**」（Query-time synthesis），知識庫本身只是被動切塊的倉庫。
  - LLM Wiki 是「**寫入時預先編譯累積**」（Ingest-time compilation），越加資料知識圖譜越完整，且人類可直接閱讀、審查與版本控制（Git）。
- **互補關係**：中小規模、重視深度理解與持續累積的研究／教學知識庫特別適合 LLM Wiki；超大規模（百萬級文件）即時搜尋則仍需搭配 RAG。
